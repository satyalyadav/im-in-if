# Free schedulers for production maintenance

Researched 2026-10-25 against provider documentation and the current repository.

## Recommendation

Use Upstash QStash Free for the next scheduler evaluation. It can call the existing protected `POST` directly with a forwarded bearer header, supports a five-minute schedule, permits up to 15 minutes for a response, and retries failed deliveries. One `*/5 * * * *` schedule creates 288 messages per day. Setting two retries means at most 864 delivery attempts for those messages if all fail within the same day, below the Free tier's 1,000-message daily limit. A multi-day outage can leave retries from prior days, so this calculation is not a hard ceiling during prolonged failures. The Free plan lists no uptime SLA. [QStash pricing](https://upstash.com/pricing/qstash), [schedule API](https://upstash.com/docs/qstash/api-reference/schedules/create-a-schedule), [retry behavior](https://upstash.com/docs/qstash/features/retry)

QStash requires a free Upstash account and an external schedule configuration, but no application code change. Upstash's terms say free accounts do not need payment information. Do not select a paid plan. [Upstash terms](https://upstash.com/trust/terms.pdf)

## Current app contract

- [`POST /api/maintenance/sweep`](../../app/api/maintenance/sweep/route.ts) requires `Authorization: Bearer <SCHEDULER_SECRET>`. It accepts no identifiers or private planning inputs and returns aggregate counts. A call that finds a sweep already running returns HTTP 200 with `skipped: "already_running"`.
- [`GET /api/maintenance/health`](../../app/api/maintenance/health/route.ts) uses the same authentication and returns aggregate status. The maintenance lock and due-work queries live in [`lib/maintenance.ts`](../../lib/maintenance.ts).
- The deletion rule checks for `ended_at` at least seven days old when the sweep runs. Five-minute scheduling does not guarantee deletion at the exact threshold. A scheduler delay or outage can extend the lag; request-time deadline checks are also documented in the [build plan](../build-plan.md).
- The existing [GitHub Actions workflow](../../.github/workflows/outing-sweep.yml) requests a five-minute cadence and gives `curl` a 20-second timeout. The report of only one scheduled run in nine hours is user-provided; this research did not investigate its cause. Keep the workflow enabled while evaluating another trigger.
- The route declares the Node.js runtime but no `maxDuration`. I did not access secrets or call the protected production routes, so production response time and the deployed Vercel function limit remain unverified.

## QStash setup outline

1. Create a QStash account on the Free plan. The provider says free accounts do not need payment information. Keep the current GitHub Actions workflow active during evaluation.
2. Create one schedule for `https://im-in-if.vercel.app/api/maintenance/sweep` with `Upstash-Cron: */5 * * * *`, `Upstash-Method: POST`, `Content-Type: application/json`, and body `{}`.
3. Set `Upstash-Forward-Authorization` to `Bearer <SCHEDULER_SECRET>`. Add `Upstash-Redact-Fields: header[Authorization]` so the saved schedule and logs redact the credential. QStash still uses the original header to send the request. Keep the secret value only in the provider configuration, not in this document or the message body.
4. Set `Upstash-Retries: 2`. This gives an initial attempt plus two retries. Set `Upstash-Timeout` above 20 seconds and below the deployed Vercel function limit. If the deployment uses the documented Hobby Fluid Compute limit of 300 seconds, `240s` leaves a one-minute margin; verify the deployed limit before setup.
5. Review QStash schedule and delivery logs, then check the authenticated health endpoint for recent successful sweeps. QStash treats every 2xx response as delivered, including the app's `already_running` response. The app's singleton lock blocks a second sweep while the recorded run is under five minutes old; a run that stays marked active longer can be reclaimed. The updates target due rows, but retries can still repeat a completed request.

This comparison is research only. No provider account or schedule was created, no secret was read, and no production request was made. The reviewed sources establish neither an exact deletion time nor a scheduler SLA for this app.
